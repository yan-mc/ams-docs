# 新时代开源 AI 音乐制作套件 —— 可行性探讨（第二版）

> 时间：2026-10-19 晚｜作者：Lead（汇总 4 路并行调研 + 本机既有软件逆向）
> 依据：`05_新方案探讨/` 下四份专项报告 —— 01_心月格式深拆、02_SVS填词、03_开源栈调研、04_DSH架构；以及第一阶段的 `03_心月套件`、`01_ai歌曲_RVC` 报告。
> 性质：**可行性/完整性讨论**，不是完整实施方案；所有【事实】均可在对应分报告找到 URL/版本/路径/行号证据。
> 一句话：**方向成立、边界清楚**。启动器/分离/换源可以很快落地；音源炼制是中等工程量；实时变声要把音频工程当主战场；**填词成歌不再是“不可行”，2026 年已有零样本 SVS 与“保旋律改词”模型，但要做成好用的编辑器仍是最大投入**。

---

## 0. 结论速览

| 设想 | 可行性 | 关键判断 |
|---|---|---|
| ① 常规启动器（去掉心月工具盒子的系统优化/会员，做环境、组件、模型、服务、更新、诊断） | **高** | 纯工程活；Tauri 2 或 Electron 均可；2–4 周 MVP。难点在“多后端运行时隔离 + 模型下载校验 + 更新回滚”，不在 UI |
| ② 保留 DSH 核心 + 基础 Agent，功能插件/skill 化，AI 与人共用一个页面 | **高** | DSH 是 MIT、Cordis「万物皆插件」；有 profile/bundle、tool、skill、jobs、subprocess、本地 HTTP 路由、React slots 页面、插件管理器；**不需要删源码**，用自定义 profile/bundle 组合即可；用户自带 DeepSeek key 是官方支持路径 |
| ③ 插件1 音源炼制 | **中高** | RVC 训练（10–30 分钟数据）与 GPT-SoVITS 微调（1–5 分钟）都成熟、可脚本化；DiffSinger 声库训练是硬骨头；「AI 校验（ASR+对齐+质量指标）」可行且是差异化 |
| ④ 插件2 人声分离 | **高** | pymss（MIT）把现代模型统一成 CLI/Python/HTTP，326 个 catalog 模型；比 UVR5 新一代；集成成本低。注意 pymss-studio 是 AGPL，别直接分发其 GUI |
| ⑤ 插件3 实时变声器 | **中高** | 底座成熟：RVC 官方 2.3 的实时 GUI + 官方 VST2/VST3（CUDA Graph 加速）、VCClient、MeanVC2 零样本流式；难点在虚拟声卡/延迟/热切换，这些必须放在**外部本地服务**，不能做成纯网页 |
| ⑥ 插件4 歌曲换源（RVC 换声） | **高** | RVC 2.3 官方推理 + index；做成队列/参数模板/A-B 试听即可；与分离插件串成流水线 |
| ⑦ V 家式「填词成歌」 | **中（比预期乐观）** | 2026 年有三条路：DiffSinger/OpenUtau 可控主路径（需自研无头渲染器+音节分配+编辑器，约 2–4 人周核心）；SoulX-Singer 零样本 SVS（Apache-2.0，最快出音）；YingMusic-Singer-Plus「保旋律改词」（CC BY 4.0，一条命令，适合草稿/批量）。**正确顺序是 SVS 干声 → SVC/RVC 换音色，不能反过来** |
| ⑧ 用户接自己的 DeepSeek API Key | **高** | 设置→模型原生支持；也可加自定义 baseURL/模型；key 存 `$DSH_HOME/.credentials.yaml`；本地推理不依赖云端 |

**三个必须先定的产品问题**：
1. 做“**工具集**”还是“**工作站**”？工具集 = 每个插件独立可用、AI 帮串流程；工作站 = 项目制 + 编辑器 + 混音导出，工程量约为前者 3–5 倍。
2. “**音源**”包含哪几类？建议先支持 RVC（换声/实时）+ GPT-SoVITS（配音）+ DiffSinger/零样本（唱歌），用统一音色包管理，但**不强行统一底层格式**。
3. 发行形态：**官方 DSH 桌面版 + 自定义 profile/插件包**（快），还是 **fork DSH 白标 + 独立启动器**（可控但跟进成本高）？建议分两阶段。

~~~text
L1 启动器层：系统/环境/组件/模型/服务/更新/诊断（心月工具盒子的有用部分 + 工程化）
~~~

## 2. 总体架构建议

### 2.1 推荐分层

~~~text
┌────────────────────────────────────────────────────────────┐
│ 启动器 Launcher（Tauri 2，独立进程）                          │
│ 硬件/环境检测 · 组件安装 · 模型库 · 服务编排 · 更新回滚 · 诊断   │
└───────────────┬────────────────────────────────────────────┘
                │ 拉起 DSH（music profile）
                ▼
┌────────────────────────────────────────────────────────────┐
│ DSH Core（MIT，profile/bundle 组合，不删源码）                 │
│ Agent 循环 · 会话 · 工作区 · 工具注册 · Skills · Jobs · 审批    │
│ ┌────────── Host 音乐插件 ──────────┐  ┌──── Client 页面 ────┐ │
│ │ music-core（任务/GPU 锁/产物/服务）│  │ 数据集工作室         │ │
│ │ trainer / separator / vc / convert│  │ 训练监控 / 分离队列   │ │
│ │ singing-studio / mixer / hub ...  │  │ 变声控制台 / 换声页   │ │
│ │                                  │  │ 填词编辑器 / 混音台   │ │
│ └──────────────────────────────────┘  └────────────────────┘ │
└───────────────┬────────────────────────────────────────────┘
                │ 只走本地 HTTP/WebSocket（同一套 API）
                ▼
┌────────────────────────────────────────────────────────────┐
│ 本地音频服务（Python/C++，按后端拆进程，由启动器管理）          │
│ RVC 训练/推理 · GPT-SoVITS · DiffSinger/SoulX · pymss · TTS   │
│ 实时音频 I/O（WASAPI/ASIO/VB-Cable） · ffmpeg · VST 宿主      │
└────────────────────────────────────────────────────────────┘
~~~

### 2.2 六条关键原则

1. **能力与 UI 解耦**：所有能力先做成“本地任务式 API”；DSH 的 AI 工具、DSH 页面、CLI、外部脚本都调同一套 API。这样即使 DSH 页面能力有限，也能用独立 SPA/iframe 兜底。
2. **DSH 只做“大脑 + 壳”**：Agent、Skill、Tool、页面、权限在 DSH；GPU/音频/模型在本地服务。**不要把推理塞进 Node 插件**。
3. **发行版用 profile/bundle 组合，不删源码**：官方明确“每个运行中的 dsh 都是插件树”，自定义 profile 只挂需要的 bundle；不需要的行 `disabled: true`。
4. **每个后端独立便携运行时**：RVC（torch 2.0/cu118）、pymss（torch 2.7+/cu128）、GPT-SoVITS、DiffSinger（ONNX）互相冲突；用 uv + python-build-standalone 按后端隔离，启动器负责装/修/回滚。
5. **统一“音色包”（UVP）+ 后端适配器**：不强行改上游权重格式；用 manifest 描述“这个音色能用哪些后端、产物在哪”。
6. **AI 与人共用“任务（Job）”抽象**：Job = {id, type, params, progress, logs, artifacts, status}；AI 创建/查询，页面展示/操作；可审计、可回滚。

### 2.3 与你设想的对照

| 你的设想 | 落地方式 | 备注 |
|---|---|---|
| 保留 DSH 核心和基础 agent，去掉没用的 | 自定义 `music` profile：dsh-base + dsh-web-app + music-bundle；其余行禁用/不安装 | 零 fork；插件管理器里也可禁用 |
| 其他功能都做成插件和 skill | Host 插件注册工具/服务/jobs；Client 插件注册页面；skill 用 markdown 工作流 | 建议拆成 core + 每功能一个插件 + 一个 UI 插件 + skill 包 |
| 封装、构建完整页面 | Client 插件可注册 `main` 全页面 + 侧栏导航 + 设置页 + 工具卡片；复杂编辑器用 Canvas/WebAudio 自研或嵌独立 SPA | 不能替换 DSH 外壳；无 URL 路由 |
| 用户接自己的 DeepSeek API | 设置→模型，或自定义 provider（openai-completions/responses/anthropic-messages） | key 只写不回显，存本地凭据文件 |

## 3. 启动器方案

### 3.1 保留 / 去掉 / 新增

**保留（重做）**：一键启动/停止、环境检测（Windows/CPU/GPU/显存/驱动/CUDA/内存/磁盘/端口）、组件安装与修复（运行时、ffmpeg、VB-Cable、VST3、7z）、模型下载/更新/校验（镜像、断点续传、sha256、离线包）、服务启停/健康检查/日志、自动更新（分通道）、诊断（日志打包/崩溃报告）。

**去掉**：64 项注册表优化、Windows Update 开关、DNS/TCP 调参、内存清理、显卡改名、FPS 浮层/Ping、VIP/钻石/充值、账号/微信登录、云端音色市场、强制更新闸门。

**新增**：DSH profile 管理、插件包安装/更新/禁用、多后端运行时管理（uv + 独立 Python、冲突检测/回滚）、音色包库（导入/来源/许可证/hash/预览）、项目/缓存/磁盘管理、API Key 引导（交给 DSH 凭据）、更新回滚/离线模式、审计日志。

### 3.2 技术选型

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **Tauri 2 + Rust** | 包小、内存低、原生进程/文件/更新能力好、Rust 下载校验稳 | 需要 Rust；依赖 WebView2 | **首选**（只做管理，收益大） |
| Electron + Node | 与 DSH 同栈、可复用 electron-updater、前端熟 | 包 150MB+、内存高、安全面大 | 团队只有 Node 时可选 |
| 纯 DSH 插件当启动器 | 零新栈 | DSH 起不来时没法修；安装/更新场景不成立 | **不推荐单独用**，可作“运行中设置页”补充 |

### 3.3 与 DSH 的关系

- 启动器负责**装/修/更新/起**；DSH 负责**用**。启动器用固定 profile 拉起 DSH（CLI `dsh --profile music` 或 Desktop），把组件路径/端口/服务 URL 通过环境变量或 profile patch 注入。
- 运行中需要“装组件/换模型/重载插件”时，插件通过**启动器暴露的本地 IPC/HTTP** 请求，并让用户确认；而不是让插件自己改环境。
- API Key 只在 DSH 里配置；启动器不接触用户 key。

### 3.4 可行性

高。工作量集中在：多运行时隔离安装/修复、模型校验与镜像、更新回滚、服务生命周期与端口/GPU 冲突处理。建议首发 Windows x64 + N 卡一条推荐配置，跑通再扩展。

## 4. DSH 承载评估（关键结论）

### 4.1 已核实事实

- 【事实】DSH 是 DeepSeek 开源的 MIT Agent Harness（`github.com/deepseek-ai/deepseek-harness`），基于 Cordis「一切皆插件」；本机桌面版 0.2.1-rc.2（Electron 44.7，内置 Node 24.21/pnpm 11.28/Python 3.12.14，安装后约 1043 MB）。
- 【事实】运行中的 dsh 是由 **profile → bundle（patch）→ 用户 cordis.patch.yml → --patch** 组合出来的插件树；bundle 在自身 package.json 的 `dsh.bundle` 声明 patch，profile 在 `dsh.profile.bundles` 列出顺序；支持 `disabled: true` 卸载某行；有兼容性门（engines.dsh）。
- 【事实】Host 插件可注册：AI 工具（`ctx.tools.register`）、skill（文件系统发现/`ctx.skills.register`）、jobs（`ctx.jobs`，进度/日志环/取消/持久 Session 事件）、本地 HTTP/WS（`ctx.webServer.register`/`registerUpgrade`）、子进程（`ctx.subprocess`，显式 argv/env、可杀进程树、无 shell 解释）、设置/凭据。
- 【事实】Client 插件（`dsh.client` + React 18 Slots）可注册：`main` 全页面（keyed slot）、`sidebar.panellist` 导航、`settings.section`、`tool.call.toolview`、`shell.overlay` 等；可嵌 iframe/webview 打开本地 HTTP 应用（loopback 允许），但不能替换 AppFrame/root renderer，**没有 URL 路由**。
- 【事实】用户自带 key：设置→模型填 DeepSeek key；也可加自定义 provider（OpenAI Chat Completions / Responses / Anthropic Messages）；key 存 `$DSH_HOME/.credentials.yaml`；也支持 `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` 环境变量。
- 【风险事实】官方标注 developer preview，会有破坏性变更；已安装 Host 插件在宿主进程内运行、**不受工作区沙箱限制**；默认挂载 session-log-deepseek（单次上限 8MiB 上传）与 telemetry，需在自有 bundle 里关闭。

### 4.2 我们的发行版组装

~~~text
@yourorg/dsh-music-profile          ← dsh.profile.bundles: [dsh-base, dsh-web-app, dsh-music-bundle]
  ├─ @deepseek-ai/dsh-base           ← 模型/工具/凭据/审批/持久化（保留）
  ├─ @deepseek-ai/dsh-web-app        ← Web UI 壳（保留）
  └─ @yourorg/dsh-music-bundle       ← dsh.bundle.patch
       ├─ music-core (host)          ← 任务/GPU 锁/产物库/音色包/服务管理
       ├─ music-trainer / separator / voice-changer / song-convert (host)
       ├─ music-singing (host + client)
       ├─ music-ui (client)          ← 页面/编辑器/播放器
       ├─ music-mixer / model-hub / evaluator (host+client)
       └─ music-skills               ← 翻唱/炼制/分离/填词/质检 SOP
~~~

**关键结论：不需要“删源码”。** 官方支持 profile 组合与 patch；你要的“只保留核心 + 必要插件”天然就是自定义 profile，其余在插件管理器里禁用即可。

### 4.3 边界与限制

| 需求 | 现实 | 结论 |
|---|---|---|
| 全页面/导航/设置/工具卡片 | Client slot 可以做到 | ✅ 可直接插件 |
| 完全替换 DSH 外壳（去掉聊天壳、像独立 DAW） | root renderer/AppFrame 不开放 | ❌ 需 fork 或走 SDK+自研前端 |
| 长时训练任务/进度/日志/取消 | ctx.jobs + subprocess 可做；但 dsh-jobs-local 是进程内注册表，**进程退出任务消失** | ✅ 管理面可做；需自研“重启恢复/重连”策略 |
| 本地 HTTP 服务 + SSE 进度 | ctx.webServer 可注册 | ✅ |
| Python/GPU 子进程 | ctx.subprocess 可 spawn、可杀进程树；环境变量默认清洗（凭据/DSH_* 不继承） | ✅，需显式传 env |
| GPU 环境安装/驱动 | 插件不做 | ❌ 交启动器/独立服务 |
| 实时音频 I/O/虚拟声卡 | 浏览器/Electron 渲染进程无原生音频设备通道 | ❌ 必须外部服务；DSH 只做控制面板 |
| 客户端插件构建链 | 官方 clientBundle preset / Typert codegen **未发布 npm** | ⚠️ 需自建构建链（可复刻，不必 fork 运行时） |
| 白标/裁剪/签名/更新 feed | productName 等硬编码；appId/feed 可 env 覆盖 | ⚠️ 产品化需 fork 构建（1–3 人日改 + 持续跟进） |
| 官方插件市场 | **目前没有官方市场**，只有用户自填索引 | ⚠️ 自建分发/索引 |

### 4.4 结论

**技术上可行，而且比从零写一个带 Agent 的应用省几个数量级。** 建议两阶段：
- **阶段一（4–8 周）**：官方 DSH 桌面版 + 自定义 bundle（Host 工具/jobs + Client 整页 + skills），验证“训练任务管理 / 音频编辑器 / 模型下载”三条主线；
- **阶段二（6–12 周）**：fork DSH 构建做白标/裁剪 + 独立 Tauri 启动器；DSH 作为本地 agent 内核（Desktop 或 `--profile sdk`）。
- 不建议：把启动器完全塞进 DSH 插件；也不建议一开始自研完整前端（重复成本高）。

## 5. 插件设计

### 5.1 公共底座 music-core

- Runtime/服务管理：发现启动器装好的后端，启停服务、健康检查、端口分配；
- Job 队列：训练/分离/推理/下载；GPU 锁、优先级、取消、断点；
- 产物库：每次任务一个 artifact 目录（输入/输出/参数/日志/预览）；
- 音色包/模型注册表：UVP 元数据、路径、hash、许可证、后端适配；
- 项目约定：目录结构、命名、采样率/格式规范；
- 事件流：进度/日志/完成事件，供页面与 Agent 订阅。

### 5.2 插件一：音源炼制（trainer）

| 目标 | 后端（2026-10 推荐） | 数据 | 产出 | 训练成本 |
|---|---|---|---|---|
| 换声/翻唱/实时（RVC） | RVC 官方 2.3.260718（MIT）；Applio 作参考 | 10–50 分钟干净人声（不需文字） | pth + index | 单卡 3060 约 10–60 分钟 |
| 配音（TTS） | GPT-SoVITS v2Pro（MIT，中文微调最实用）；Qwen3-TTS（Apache，3 秒零样本+流式）作快捷 | 1–5 分钟＋准确文本；参考音频 3–10 秒 | GPT ckpt + SoVITS pth + 参考音频 | 1–2 小时 |
| 唱歌合成（SVS） | DiffSinger 声库训练（Apache）；SoulX-Singer 零样本（Apache）作快捷 | 1–3 小时标注演唱 | 声库（ONNX + 词典 + 配置） | 单卡 3060 约 1–3 天 |
| 零样本（不训练） | SoulX-Singer（SVS）、SoulX-Singer-SVC（换音色）、MeanVC2（实时 VC）、Qwen3-TTS | 3–30 秒参考音频 | 运行时参考 | 0 |

**流程**：导入素材 → **AI 校验**（ASR 转写与文本比对、强制对齐、SNR/削波/混响/静音、说话人一致性）→ 自动清洗（分离/去混响/降噪/切片）→ 训练（Job）→ 评测（相似度/音高/可懂度/抽听）→ 导出 UVP → 注册音色库。

**AI 工具示意**：`voice_dataset_inspect`、`voice_dataset_clean`、`voice_train_start/status/cancel`、`voice_evaluate`、`voice_export`、`voice_list`。

**可行性**：中高。RVC/GPT-SoVITS 都有成熟脚本；真正的工作量是数据集校验/清洗、任务管理、UVP 打包与许可记录。

### 5.3 插件二：人声分离（separator）

- **首选 pymss**（MIT，v2.1.9；326 个 catalog 模型；BS/Mel-Band Roformer、SCNet、HTDemucs、VR；分块+overlap-add+TTA+ensemble；CLI/Python/HTTP/workflow）。
- 备选：audio-separator（MIT，嵌入库）、MSST（MIT，SOTA 模型/训练来源）、UVR 5.6（MIT，2026-10-06，GUI/模型参考）。
- 能力：2 轨/4 轨/6 轨、去混响 `dereverb_*`、去和声 `karaoke_*`/`chorus_*`、单乐器 mega-53、多模型 ensemble、批量。
- 注意：pymss-studio 是 **AGPL-3.0**，若要分发其 GUI 需合规；建议只用 MIT 的 pymss 包 + 自研页面。
- 可行性：高。

### 5.4 插件三：变声器（voice-changer）

- **首选**：RVC 官方 2.3.260718 实时 GUI + **官方 VST2/VST3（Win64）**；CUDA Graph 官方实测算法延迟最高 4.7× 加速；支持 50 系/AMD·Intel 整合包。
- 备选：VCClient 2.1.4-alpha（MIT；RVC/Beatrice）、MeanVC2（Apache-2.0，流式零样本 VC）、so-vits-svc-fork（AGPL，维护中，仅备选）。
- 明确排除：Seed-VC（GPL+已归档）、so-vits-svc 原版（AGPL+已归档）——不应作为新方案必选依赖。
- 必须做：虚拟声卡安装/检测（VB-Cable/VoiceMeeter）、设备枚举/独占、延迟/缓冲/热切换、监听/增益、崩溃自恢复、录音。
- 架构边界：**实时音频必须外部本地服务**（原生/Python），DSH 只做控制面板与状态；页面内做低延迟音频路由不可行。
- 可行性：中高；难在音频工程而非模型。

### 5.5 插件四：歌曲换源（song-convert）

- 定义澄清：你说的“用 VITS 方案换声音”准确说是 **RVC（VITS 系）音频→音频换声**；GPT-SoVITS 是“文本→语音”，不做换声。
- 流程：分离出的人声 → RVC 2.3 推理（模型+index、pitch、f0 方法、index_rate、protect）→ 与伴奏对轨/混音。
- AI 工具：`convert_run`（参数模板）、`convert_batch`、`convert_ab`、`convert_artifacts`。
- 可行性：高。主要注意 40k/48k 采样率一致与批量任务管理。

## 6. 音源格式与“炼制”到底是什么

### 6.1 各后端需要的“音源”不是同一种东西

| 用途 | 后端 | 产物 | 关键参数 | 训练数据 |
|---|---|---|---|---|
| 换声/翻唱/实时（VC/SVC） | RVC v2 | `.pth`（约 55MB）+ `.index`（faiss，约 130MB） | 40k/48k、f0=1、v2、emb_g 说话人数 | 10–50 分钟干声（不需文字） |
| 配音（TTS） | GPT-SoVITS v2Pro | GPT `.ckpt` + SoVITS `.pth` + 参考音频 | 32kHz、参考文本、语言 | 1–5 分钟＋文本 |
| 唱歌合成（SVS） | DiffSinger/OpenUtau | 声库目录（ONNX 声学+声码器+词典+配置） | 语言/音素集、音高范围、44.1k | 1–3 小时标注演唱 |
| 零样本 | SoulX-Singer / MeanVC2 / Qwen3-TTS | 无需训练，参考音频即可 | 3–30 秒参考 | 0 |

所以“音源炼制”应按目标拆模式；**“语音+文字让 AI 校验”主要适用于 TTS 数据集**，RVC 只需音频质量校验，SVS 还需要音高/歌词标注。

### 6.2 统一音色包 UVP v0.1（建议）

来自 03_开源栈调研：目录 + `manifest.json` + 多后端 `backends[]` + `training/` + `license/` + `hashes`；推理端按 `kind/capability/硬件/延迟` 过滤并 fallback；训练管线 `validate→train→eval→pack→sign`。

~~~text
voice_pack/
├─ manifest.json          # format/voice_id/kind/languages/engine_preference/backends[]/license/hashes
├─ models/
│  ├─ rvc/<name>.pth + .index
│  ├─ gptsovits/<gpt>.ckpt + <sovits>.pth
│  ├─ diffsinger/<voicebank>/...
│  └─ onnx/ · gguf/
├─ refs/                  # 参考音频 + 转写 + 语言/情绪/时长
├─ preview/               # 试听样本 + 封面
├─ training/              # dataset.json / config 快照 / metrics.json / log
└─ license/               # VOICE_SOURCE.txt（声音授权）+ third_party.json
~~~

示例 manifest（节选）：
~~~json
{
  "format": "uvp", "format_version": "0.1",
  "voice_id": "elv_zh_f_01", "display_name": "爱莉希雅（自制）",
  "kind": ["singing", "tts"], "languages": ["zh", "en"],
  "engine_preference": ["rvc", "gptsovits"],
  "backends": [
    { "id": "rvc", "type": "rvc", "sample_rate": 48000,
      "capabilities": ["singing", "speech"],
      "files": { "model": "models/rvc/elv.pth", "index": "models/rvc/elv.index" },
      "params": { "f0_method": "fcpe", "index_rate": 0.75, "protect": 0.33 },
      "requirements": { "vram_mb": 2048, "backend_version": ">=2.3.260718" } },
    { "id": "gptsovits", "type": "gpt_sovits", "sample_rate": 32000,
      "capabilities": ["tts"],
      "files": { "gpt": "...", "sovits": "..." },
      "refs": [ { "audio": "refs/ref_zh_01.wav", "text": "参考文本", "language": "zh" } ] }
  ],
  "training": { "dataset": { "total_sec": 620, "snr_db_median": 28.4 },
                "metrics": { "speaker_similarity_cos": 0.86, "utmos": 3.4 } },
  "license": { "voice_source": { "type": "self", "commercial_use": true } },
  "hashes": { "algo": "sha256", "files": { } }
}
~~~

机器可读 schema 见 `03_开源栈调研/voice_pack.schema.json`。

### 6.3 AI 校验可以做成什么

- 转写一致性：faster-whisper/FunASR/WhisperX 转写 vs 用户文本 → 标出差异；
- 强制对齐：MFA/WhisperX/TIFA → 词/音节起止时间；
- 音频质量：采样率/位深/响度/削波/静音/底噪/混响（DNSMOS/UTMOS 或简单指标）；
- 一致性：说话人 embedding 相似度、音高范围、语速；
- 清洗建议：切片、去混响、降噪、剔除不合格片段；
- 训练后评估：试听文本合成、相似度、音高 RMSE、可懂度、人工抽听清单。

### 6.4 心月模型格式拆解（已实测：能拆、能转回标准 .pth）

**【硬结论 1｜MSVC → 标准 RVC v2 .pth：能，已实测成功】**（详见 `01_心月格式深拆/报告.md`、`格式.md`）
- 容器格式：14 字节头（`MSVC` + `01 00` + `XINYU_AI`）+ **3 条「u32 长度 + 整段字节反转的 payload」** + 16 字节 trailer；逻辑内容 = 4 段 metadata（1692 B）+ 张量表 JSON（50,824 B）+ **明文 FP16 权重**（57,433,988 B）。
- 457/457 张量全部还原：JSON 表碎片拼接完整、`length = prod(shape)*2` 全通过、sum(length) 与物理数据分片逐字节闭合 → **权重是明文，没有做内容加密**。
- 生成 `samples/爱莉希雅.msvc_reconstructed.pth`（57.6 MB，457 张 fp16 + config/info/sr/f0/version）。
- 用 RVC20260311 的 runtime 加载标准 `SynthesizerTrnMs768NSFsid`：`load_state_dict(strict=False)` → **unexpected=0**，missing=103 且**全部是 enc_q.***（RVC 推理模型本就不含后验编码器，属正常）；`infer()` 实测返回 `(1,1,48000)` 音频、数值有限，输出 `samples/infer_test.wav`。
- 也就是说：**它没有改模型架构，只是“容器混淆 + 分片重排 + 机器指纹/唯一码 + 授权校验”**；`encryption_level=enhanced` 的“增强”主要加在容器与记录 TLV 上，而不是权重加密。

**【硬结论 2｜.cyd/Fernet：静态不能解密】**
- 明文产物（main.pyc、Guipro.pyd、pyz、strings）里**没有密钥或派生逻辑**；.cyd/.bgx/data.bin 熵 7.9–8.0（接近随机）。
- 另有一套 encrypted-pth：文件尾身份牌 `XINYU_OFFICIAL_IDENTITY_CARD_2024`，解密函数 `infer.lib.encode.smart_pth_decrypt_data(_with_identity)` 位于**加密的 encode.cyd 内部**（自锁）；客户端还采集 MachineGuid/主板/BIOS/UUID 做机器绑定。
- 要解密只能动态调试心月服务/内存 dump（需要运行其服务，本次按只读规则未做）。→ **新方案不要依赖它的加密模块**。

**【对产品的含义】**
- 技术层面：开源栈可以做「**.msvc 只读导入器**」（TLV 解析 → metadata → JSON 碎片拼接 → 按 offset/length 抽 FP16 → 组 state_dict → 存 .pth）。注意分片顺序与 JSON 边界是混淆的一部分，需“布局推断 + 人工校验”，不要硬编码偏移；另两个 .msvc 还需交叉验证（本次已证明格式同构但只完整验证了爱莉希雅）。
- 合规层面：**不导出、不打包、不分发其权重**；最多让用户在本机把自己合法拥有的文件转成开源格式（个人数据迁移/互操作），并明确风险（可能违反其用户协议，且音色涉及角色/声音人格权）。
- 新方案主线只支持标准 RVC / GPT-SoVITS / DiffSinger / UVP；心月只作为“格式逆向案例 + 交互参考”。

## 7. 填词成歌（V 家式）可行性

### 7.1 2026 年全景（关键候选）

| 方案 | 输入 | 许可 | 特点 | 适用 |
|---|---|---|---|---|
| **DiffSinger（OpenVPI）+ OpenUtau** | 音符+音素+时长+F0（.ds）；OpenUtau 工程 | DiffSinger Apache-2.0；OpenUtau MIT；**声码器 openvpi/vocoders 为 AGPL** | 可控性最好、可离线、中文声库多；OpenUtau **无 CLI**，需自研无头渲染；声码器许可要处理 | **产品主路径（编辑器）** |
| **SoulX-Singer**（2026-02） | 歌词 + MIDI/F0 + 10 秒音色参考 | **Apache-2.0（代码+权重）** | 零样本 SVS，42k 小时数据；CLI/Gradio/HF Space；输入是内部 JSON 元数据，MIDI 友好输入仍在 roadmap | **零样本快捷通道** |
| **YingMusic-Singer-Plus**（2026） | 旋律参考人声 + 新歌词（+可选音色参考） | **CC BY 4.0**；VAE 部分 Stability 社区许可 | 「保旋律改词」一条命令（--melody_audio + --target_text），内置分离/混伴奏；不是编辑器级可控 | **已有原曲换词 / 草稿 / 批量** |
| **ACE-Step 1.5**（2026） | 歌词+风格（+src_audio cover） | **MIT（代码+权重）** | 整曲生成/cover/repaint；3090 整曲 <10s；旋律不可逐音控制 | 整曲兜底/编曲 |
| **YuE2**（2026-09） | 歌词+风格→ABC 乐谱→渲染 | 代码 Apache；**权重 CC-BY-NC-4.0** | 符号化、可读可改谱，最接近“改谱填词”；24GB BF16、Linux | 仅研究/非商用 |
| 其他 | NNSVS（停更）、VISinger2（无 LICENSE）、NEUTRINO（闭源日文）、Sinsy、UTAU | 各异 | — | 不推荐新建依赖 |

**混合路线顺序（很重要）**：SVS 干声 → SoulX-Singer-SVC / RVC 换音色；**不能先 RVC 再 SVS**（SVC 输出是音频，不是可用于 SVS 的标注）。

### 7.2 三条候选管线

**管线 A（推荐主路径，可编辑/可商用）**
~~~text
旋律（MIDI / 分离人声转谱 / 手绘）
  → 音符切分 + F0（GAME/SOME 或 MIDI）
  → 人工校正（最小 piano-roll）
  → 歌词 → pypinyin/jieba 注音 → 音节↔音符分配（自动+拖动）
  → 生成 .ds（音符/音素/时长/滑音，可选 variance 参数）
  → DiffSinger 声学 ONNX + variance ONNX → NSF-HiFiGAN 声码器 ONNX → 干声
  →（可选）SoulX-Singer-SVC / RVC 换目标音色
  → 与伴奏对齐/混音 → 导出
~~~
优点：许可干净、离线、逐音符可控、可接任意中文声库。缺点：需自研无头渲染器、音节分配器、最小编辑器（核心约 2–4 人周【推断】）。

**管线 B（零样本，最快出音）**：歌词 + MIDI/音符 + 10 秒音色参考 → SoulX-Singer（score 模式）→ 干声 → 混音。适合“上传音色即用”；音色相似度/稳定性需 A/B。

**管线 C（已有原曲直接改词）**：原曲 → 分离人声 → 旋律 clip + 原词 + 新词 → YingMusic-Singer-Plus → 新干声 → 混伴奏。一条命令出结果，适合 demo/批量，不是编辑器。

**建议产品形态**：A 为主（编辑器 + 通用声库），B/C 作为“加速/兜底模式”一键切换；没有 MIDI 时先用 C 出草稿，再进 A 精修（共享一套歌词/音节数据结构）。

### 7.3 编辑器最少交互（MVP，10 项）

1. 导入/生成旋律（MIDI/ustx/上传歌曲自动转谱）；
2. 歌词输入与分句：整段粘贴 → 自动分词注音 → 按音节数分配，支持 | 分句；
3. 音符级编辑：拖动音高/时长、增删、连音、休止/呼吸；
4. 音节分配修正：一字多音/多字一音，拖拽换位；
5. 试听与局部重渲染（缓存/增量）；
6. 音素面板（声母/韵母时长、替换、查看序列）；
7. 表情控制 3 个滑杆（气声/张力/能量），进阶颤音；
8. 音高曲线自动 + 可拖控制点 + “重绘”按钮；
9. 音色选择（声库下拉/零样本参考音频）；
10. 导出（干声/混音/工程）+ 署名与许可提示。

判断标准：普通用户从“粘贴歌词”到“听到第一句”≤3 次点击；专业用户可下钻音素/参数层。

| 训练/推理成本 | 数据 | 硬件 | 时间 |

### 7.5 许可雷区（必须处理）

- DiffSinger 代码 Apache-2.0，但 **openvpi/vocoders 声码器是 AGPL-3.0**：建议只分发未修改的 ONNX，或改用 MIT 的 openvpi/SingingVocoders；
- 社区中文声库多为**非商用/自定义 ToS**（例如 Tiger 为 CC BY-NC-ND + Commons Clause；绮萱为自定义条款）→ 产品默认声库需法务确认，最好让用户自行导入；
- SoulX-Singer Apache-2.0（含“不得未经授权模仿真人”使用声明）；YingMusic CC BY 4.0（需署名）+ Stability VAE 条款；YuE2/SheetSage2 权重 **CC-BY-NC-4.0** 禁商用；
- RMVPE 仓库无 LICENSE 文件 → 换有明确许可的 F0 模型或自训；
- 输出歌声涉及词曲版权与音色授权，产品需加 AI 生成标识与授权声明。

### 7.6 结论

**“给定旋律 + 音源 + 新词 → 唱出来”在开源世界已经可行，但不存在开箱即用的一体化产品。** 最现实的产品路径是：**DiffSinger 编辑器主路径 + SoulX 零样本加速 + YingMusic 改词兜底**，并把编辑器/无头渲染/音节分配作为核心自研资产。工作量不小，但比“自研 SVS 模型”现实得多。

## 9. 风险清单

### 9.1 技术风险
- **DSH developer preview**：两个月内 6 个升级指南版本，插件 API/配置可能破坏性变更 → 锁版本 + 回归 + 保留 fork；
- **多后端依赖地狱**：torch/CUDA/Python 版本冲突 → 每后端独立环境；
- **显存/并发**：训练与分离同时跑会 OOM → GPU 锁/队列；16GB 显存要限制并发；
- **实时音频**：Windows 驱动/虚拟声卡/延迟/回声/断音调试成本高；
- **SVS 质量**：DiffSinger 可控但离 SynthV 有差距；零样本音色相似度/稳定性待实测；社区声库质量参差；
- **AI 可靠性**：Agent 调参可能“看起来对但听感差” → 必须有人工试听/验收、可回滚参数、A/B 对比。

### 9.2 许可/法律风险
- DSH MIT 可改可分发，但 **「DeepSeek Harness」是注册商标**：产品名需改名或用 DSH 缩写/描述性表述；
- pymss-studio AGPL、openvpi/vocoders AGPL、DiffSingerMiniEngine AGPL、pedalboard/matchering GPL、ChatTTS AGPL、Seed-VC/so-vits-svc AGPL/GPL → 进程隔离或不分发；
- 模型/声库权重许可与代码许可分离；社区音色/角色声库多非商用；ffmpeg（LGPL/GPL）、VB-Cable 再分发条款、VST3 插件许可都要核对；
- 心月资产：逆向/解密/转发有法律与道德风险；只做用户自有资产的本机互操作，不公开分发；
- 深度合成合规：声音授权、AI 生成标识（《人工智能生成合成内容标识办法》2025-09-01 施行）、平台规则。

### 9.3 产品风险
- 范围过大：启动器+DSH+4 插件+编辑器+混音，容易做成“半成品集合”；
- 用户预期：开源 SVS 达不到商业 V 家体验，需要明确“可 AI 协作的开源工作流”定位；
- 上游更新/维护：适配层持续消耗人力；
- 成本：开发人力 + 代码签名/分发 + 模型托管带宽；
- 安全责任：用户 API key、插件任意代码、模型下载，需明确免责与校验。

## 11. 待你决策的开放问题

1. **产品定位**：工具集还是工作站？
2. **填词成歌目标**：先做“能唱对+音色像”（混合/零样本路线），还是一上来就做“精细可控编辑器”？
3. **发行形态**：先官方 DSH 桌面版 + 自带 profile（快），还是直接 fork 白标（慢但体验统一）？
4. **音源范围**：只支持标准格式，还是也兼容心月 .msvc（仅用户自有资产只读导入）？
5. **平台**：Windows x64 + N 卡优先，还是首发就要 macOS/Linux？
6. **模型/声库分发**：接受“应用不内置权重、用户自行下载/导入”的模式吗？（能绕开大部分许可问题）
7. **DeepSeek API 定位**：只做规划/文案/校验，还是也做混音/编曲建议？
8. **是否首发实时变声**：它决定要不要先做虚拟声卡/音频服务。
