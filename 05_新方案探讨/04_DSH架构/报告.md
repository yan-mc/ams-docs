## 0. 结论摘要（先看这里）

1. **技术上可行，而且 DSH 的插件模型相当适合本设想**。DSH 是 Cordis 的「一切皆插件」架构：Agent 循环、工具、会话、模型适配器、UI 全部是插件；第三方能力通过 npm 包（bundle）+ profile patch 挂载，无需改内核。【事实】
2. **「AI 音乐插件套件」可以基本不改内核实现**：AI 工具（音频处理/训练编排）、skill（乐理/流程指令）、后台长任务（jobs + 进度 + 日志 + 会话内持久记录）、子进程（Python/GPU 任务）、本地 HTTP 服务、Web 页面（React slot 面板/侧栏页/设置页/工具卡片）都有正式扩展点。【事实】
3. **「完整页面」可以做到「DSH 外壳内的全页面 + 导航入口」，但做不到「完全替换 DSH 外壳」**。客户端是固定 AppFrame（侧栏 + 会话 + 右栏）＋ React Slot 组合；插件能向 main 槽注册整页、向 sidebar.panellist 加导航，但没有 URL 路由、不能替换 root renderer。若产品要求「打开就是自己的 DAW 界面、不带聊天壳」，需要 fork 客户端壳，或走独立启动器 + SDK 方案。【事实 + 推断】
4. **用户自带 DeepSeek API key 是官方支持路径**：设置 → 模型 里填 key，也可加第三方/自定义 baseURL 提供商（OpenAI Chat Completions / Responses / Anthropic Messages 三种协议），key 存 $DSH_HOME/.credentials.yaml；也支持 DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL 环境变量；官方账号登录是可选路径。【事实】
5. **分发与更新：MIT 允许二次分发/改名/闭源附加插件，但「产品级分发」要自己承担构建、签名、更新源**。官方 Desktop 是 Electron + 内置 dsh 运行时（安装后约 **1043 MB**），更新走 electron-updater + 自有 feed；仓库默认 productName 硬编码、appId 可用环境变量改、更新源可配置，但「白标 + 裁剪」需要 fork 构建脚本重新打包。【事实 + 推断】
6. **不建议「启动器做成 DSH 的一个页面」作为唯一形态**。启动器的环境检测/组件安装/更新/服务启停涉及管理员权限、系统级操作与原生产物，放在 DSH 宿主插件里既受进程/沙箱/审批模型限制，又增加与 DSH 版本升级的耦合。推荐：**MVP 用 DSH 插件/页面（复用聊天、设置、权限、任务 UI）；产品化再补独立启动器（Tauri），DSH 作为本地 agent 内核（CLI dsh web 或 Desktop 安装包 / --profile sdk JSON-RPC）**。【推断，见 §7/§9】
7. **最大风险不是「能不能」，而是「DSH 是开发者预览、API 不稳定 + 体积/签名/更新基建 + 第三方插件无沙箱」**。官方 README 明示会有破坏性变更；2 个月内升级指南已有 6 个版本；插件在宿主进程内运行、不受工作区沙箱限制。【事实】

## 2. DSH 是什么（架构底座）

### 2.1 「一切皆插件」的 Cordis 架构【事实】
- 产品没有需要打补丁的特权内核：模型适配器、工具注册表、会话日志、agent loop 本身都是插件，可被配置替换；扩展方式是「把插件挂到其他插件旁边」，注册是可撤销副作用（ctx.effect()/ctx.on()，dispose 时撤销）。证据：evidence/repo-sparse/docs/architecture.zh.md:5-9。
- 框架是 Cordis（本仓库 vendor 版，包名 @deepseek-ai/cordis 4.0.5）：插件是「导出 apply(ctx) 的函数 / 对象 / Service 子类」，用 inject 声明服务依赖，服务占据稳定 ctx.<key>（如 ctx.tools、ctx.jobs、ctx.subprocess、ctx.slots）；事件有 emit/waterfall/parallel/serial/bail 五种分发模式。证据：unpacked/dsh/node_modules/@deepseek-ai/cordis/README.md；evidence/repo-sparse/docs/cordis-primer.zh.md:5-30；docs/user/develop/basic/index.zh.md:15-100。

### 2.2 Profile / 组合包（bundle）/ patch 三层组装【事实】
- **profile**：$DSH_HOME/profiles/<name>/ 下的具名组装，package.json 的 dsh.profile.bundles 是有序组合包列表，另有用户自己的 cordis.patch.yml。随附模板：web、headless、sdk、sdk-minimal、acp；Desktop 独占 desktop profile。
- **bundle（组合包）**：带 package.json 的 npm 包，dsh.bundle.patch 指向一个/一组 patch 文件；patch 按 id 覆盖目标行（**替换整个 config，不做深合并**）或 insert 新行。
- **加载顺序**：① 各 bundle patch（按 dsh.profile.bundles 顺序）→ ② profile 的 cordis.patch.yml → ③ $DSH_HOME/cordis.patch.yml（home 级）→ ④ 每个 --patch overlay（按 argv 顺序）。后层按 id 覆盖前行。
- **禁用行**：patch 中 disabled: true 可卸载某行而不删除条目（docs/cordis-tutorial/06-composition-and-hmr.zh.md:16-19）。
- **兼容性门**：安装与启动都会检查 bundle 的 engines.dsh（未声明则检查 @deepseek-ai/dsh* peer 范围）；不兼容需用户显式确认 version-exemptions（存 profile 的 compatibility.json）。
- 证据：unpacked/dsh/node_modules/@deepseek-ai/dsh-app-boot/README.zh.md（Profile 章节）；evidence/repo-sparse/docs/user/develop/basic/publish.zh.md:13-14,140-175；unpacked/dsh/node_modules/@deepseek-ai/dsh-plugin-manager/README.zh.md:67-77。

### 2.3 发行形态【事实】
- **CLI（npm）**：npx @deepseek-ai/dsh web 默认在 http://127.0.0.1:3080 起 Web UI；dsh --profile headless "job"、dsh --profile sdk（stdio JSON-RPC）、dsh --profile acp（自动化协议）等。（evidence/repo-sparse/README.md:11-40；unpacked/.../dsh/README.zh.md 入口模式表）
- **Desktop（Electron）**：Electron 壳 + 签名资源内**精确匹配版本**的 dsh 运行时；Electron 以 Node 模式启动私有 Desktop Host，Host 跑完整 Web 应用；窗口从 dsh-app://app/ 加载打包 Web 资源，HTTP 请求转给已认证 Host，WebSocket 连 Host。安装后约 1.04 GB（本机实测）。证据：evidence/repo-sparse/apps/desktop/README.zh.md:31-57,139-190；本机目录实测。
- 发布节奏：近 3 天连续发布 0.2.1-alpha.3/4/5、rc.1、rc.2（GitHub releases 列表，2026-10-14～10-17），README 明示 developer preview、会有破坏性变更（README.md:8-14）。

### 2.4 随发行版自带的核心组合【事实】
- dsh-base 96 行：模型连接、完整工具集（fs/shell/web/search/subagent/jobs/goal/todo/skill/MCP/plan…）、持久会话、沙箱与审批、设置、凭据、遥测；dsh-web-app 116 行：在 base 上加 Web 传输、API controller、全部 UI 客户端插件、presets、账号/市场等。行清单见 evidence/repo-sparse/packages/bundle/base/cordis.patch.yml、packages/bundle/web-app/cordis.patch.yml（本次统计 96 / 116 行）。
- 这 96+116 行就是「保留核心 / 裁剪」的操作面。

## 3. 插件模型（问题 1）

### 3.1 服务端插件：如何注册、清单/入口/生命周期【事实】
- **入口契约**：插件是一个 ESM 模块，导出 apply(ctx, config)；可选 name、inject（服务名数组）、Config（Schemastery schema）。三种形态：函数、对象（export default { name, inject, apply }）、Service 子类（class X extends Service，用于提供服务）。（evidence/repo-sparse/docs/user/develop/basic/index.zh.md:15-135）
- **生命周期**：Cordis fiber；inject 的服务未就绪时插件保持 PENDING；注册即 effect，dispose 自动撤销；手动资源用 ctx.effect(() => cleanup)；热重载（HMR）时按插件 fiber 串行卸载/重载。可选插件启动失败只警告，required 行失败会终止启动（app-boot 失败矩阵）。
- **注册/挂载**：① 在 profile 的 cordis.patch.yml 里 insert 一行 { id, name }（name 可为包名/绝对路径/file URL）；② 打成 npm bundle（dsh.bundle），用 dsh plugin --profile <p> add <spec> 或 Web/Desktop 插件管理器安装；③ --patch 一次性 overlay。【事实】
- **安装来源**：npm registry（含私服/registry 列表回退）、Git 仓库（安装前 git ls-remote 预检，源码包需作者提供 prepare 构建并需用户批准 build scripts）、本地目录 link:/file:、tarball。安装使用 profile 内 pnpm（Desktop 内置 pnpm，不依赖 PATH）。【事实】（dsh-plugin-manager README:40-77）
- **HMR**：dsh-hmr 监视 profile manifest 与 profile/home patch，配置改动实时重组；未启用时改动需重启。【事实】（architecture.zh.md；dsh-plugin-manager README）

### 3.2 客户端插件：如何注册、清单/入口/生命周期【事实】
- **清单**：包 package.json 声明 dsh.client = { platform: 'web', inject?: 包名边[], immediately?: bool, external?: 精确模块请求[] }，并导出 exports["./client"]。
- **入口格式**：不是普通 ESM，而是 **lazy-CJS closure factory**——bundle 执行时只调用 window.__ModuleLoader__.load({ id, factory: (require) => {...} }) 注册工厂，模块副作用（含 CSS 注入）在物化时才运行；import() 被编译成 require.async("./client.<name>.js")（自包含 chunk）。
- **加载**：Host 半侧增量扫描 Loader 条目中声明 dsh.client 的包，组合成 window.__DSH_BOOT__ 图，在 /plugins/??...&rev=... 提供 combo 脚本，/plugins/events SSE 推送图/重建事件；浏览器半侧按需物化。
- **共享模块**：冻结的 PLATFORM_MODULES 表＝react、react/jsx-runtime、react-dom、react-dom/client、@deepseek-ai/cordis、zod、@tanstack/react-virtual、dsh-client-store、dsh-client-ui-slots、dsh-client-ui-primitives、dsh-client-ui-dockkit（evidence/repo-sparse/packages/client/web/src/platform.ts:8-12）；超出基座的三方库由插件自带（打进 lib/client.js）。
- **构建要求**：pnpm run build 必须已产出每个 lib/client.js；构建 preset clientBundle 位于仓库 packages/client/tsdown.client.ts，**不在任何已发布 npm 包里**，仓库外插件需自行复刻构建（client-modules README「构建要求」；cookbook adding-a-settings-card 亦明示）。
- **HMR**：dsh-client-hmr 轮询 bundle stat + /plugins/events SSE，代码重建后替换插件（React 状态丢失、数据层保留）；**只服务 Web 传输**，Electron 安装/重启流程不用该 SSE 路径。开发时 pnpm run dev:web 同时起 host 与 rebuild watcher。
- 证据：unpacked/dsh/node_modules/@deepseek-ai/dsh-client-modules/README.zh.md:32-53；docs/subsystems/client-modules.zh.md；unpacked/.../dsh-client-hmr/README.zh.md；evidence/repo-sparse/packages/client/tsdown.client.ts:1-30,115。

## 4. 页面与前端能力（问题 2）

### 4.1 技术栈【事实】
- Web 客户端是独立加载的浏览器侧 Cordis 应用：Client Modules（插件图）＋ API Gateway（类型化 Host 通信）＋ React Slots ＋ Conversation。React **18.2**、Vite 6.4、TypeScript 6.0、zod 4.4.3、@tanstack/react-virtual 3.14.10（packages/client/web/package.json、apps/web/package.json）。
- 槽位系统：类型化注册表 + 生命周期账本；ctx.slots.register() 注册组件，ctx.slots.inject(key, cb) 等待某声明出现；single/list/keyed/chain 基数 + root/session-maybe/session scope；组件 props 由五类 share 推导（owner props / children renderers / store / inject face / locale）；组件**收不到 ctx**。证据：docs/subsystems/slots.zh.md。
- 布局：三栏 AppFrame（左 264–420px 可折叠、中栏会话、右栏 dock 面板）；main keyed slot 的全局面板（ctx.layout.selectPanel(id) 切换，conversation 是保留 key）；sidebar.panellist 是左侧导航贡献点。**没有 URL 路由**：客户端 shell 的 bundle 中未发现 pushState/location 路由（本次 grep 0 命中），页面状态由 layout 选中态管理。【事实 + 推断】
- 可嵌入：ui-sidebar-browser 在 Web 用 sandbox iframe（allow-scripts allow-forms allow-same-origin allow-popups allow-popups-to-escape-sandbox），Desktop 用 Electron webview（guest 租约、无 Node/preload），**允许 loopback HTTP(S)**，Web profile 默认关闭、Desktop 默认开启；本地文件走 Document Preview（HTML 支持「静态净化 iframe」与「支持脚本的 Blob 交互预览」两种模式）。证据：dsh-client-ui-sidebar-browser/README.zh.md:12,30-31,57-95；dsh-client-ui-sidebar-documentpreview/README.zh.md；docs/subsystems/sidebar-right.zh.md:146。
- 音频：浏览器侧可用 MediaRecorder / Web Audio（语音输入插件即此实现，含输入电平预览、设备选择、PCM 转换后送 Host）；本地 STT 走 sherpa-onnx（Host 侧）；无流式识别、无 TTS。证据：dsh-experimental-client-ui-voice-input/README.zh.md。

### 4.2 能做到什么程度的「完整页面」【推断，附依据】
- **可以**：注册一个全页面（main keyed slot），在左侧导航加入口（sidebar.panellist），页面内自由用 React/Canvas/WebAudio/SVG；用 ctx.layout.selectPanel() 切换到它；注册设置页、工具卡片、聊天节点、右栏页签、overlay。参考 ui-schedule 的「任务管理整页 + 右栏详情页签 + 侧栏入口 + 会话内卡片」全套实现（packages/client/ui-schedule/src/client/index.ts:155-184）。
- **可以**：嵌入现有的本地 Web 应用（如自研 Vite/React 音频编辑器）——起本地 HTTP 服务（插件 ctx.webServer 或独立进程），用 sidebar browser 的 iframe/webview 打开 http://127.0.0.1:<port>；但 iframe 与 DSH 页面**跨源隔离**：被嵌入页面不能读 DSH DOM/API，DSH 插件也不能直接操作 iframe 内部（只能靠 postMessage/URL 参数）。【事实：sidebar-right 文档 + iframe 策略；推断：集成方式】
- **受限**：① 不能替换 AppFrame/root renderer，聊天壳、侧栏、输入框始终存在（要隐藏只能 fork）；② 无 URL 路由/深链；③ 客户端插件构建链需自建（preset 未发布）；④ 大编辑器依赖需自己打包进 client.js（React 之外的库都算 plugin-private，bundle 会变大）；⑤ HMR 重载会丢组件状态（保存草稿要放 Host 或浏览器存储）；⑥ 浏览器环境无原生文件系统/原生菜单/原生音频设备（麦克风除外，走浏览器权限）。
- **桌面（Electron）额外限制**：Desktop 只给主 dsh-app://app 文档开麦克风权限；webview 仅主窗口启用、guest 无 Node；本地文件预览由 Document Preview 负责；所有原生能力（打开方式、目录选择、托盘、更新）归 Electron 壳，插件只能通过既有 Remote/HTTP 使用。

## 5. 技能、工具、长任务与 API Key（问题 3）

### 5.1 skill 机制【事实】
- 文件格式、发现根与 rank、watch、调用策略（modelInvocable/userInvocable）见 §3.3 与 dsh-skill-filesystem/README.zh.md:34-60；dsh-tool-skill 把目录渲染进会话，按需加载正文（≤8192 字符阈值相关说明见 dsh-agent-preset README）。
- 对音乐产品的用法：把「写歌/编曲/混音/训练数据准备」的流程、风格规范、工具使用约束写成 skill，随 bundle 的 bundledSkillDir 或项目 .dsh/skills 分发；不需要改代码即可迭代提示词资产。

### 5.2 tool 机制【事实】
- defineTool：类型化参数（string/number/integer/boolean/null/array/object/json/oneOf，16 层容器内保留类型）、output.schema + render、execute(args, exec)（exec.signal 协作取消）；模型参数执行前校验；未知/异常工具转结构化错误，不终止轮次。
- 流水线：tools/pre-execute（allow/deny/ask 门禁）→ 单调 guard → tools/execute → tools/post-execute（可替换结果）→ finalizeContent → tools/result（只读）。
- 两种呈现模式：native（每个工具一个 schema）或 ptc（只暴露 run_code + 生成 SDK；Node 默认 120 s、上限 600 s，含嵌套工具与审批等待）。
- 审批/沙箱：审批策略（dsh-approval / permission）、danger-full-access / workspace-write / read-only 沙箱、Windows ACL 受限令牌；插件管理器操作要求 danger-full-access 或单次批准；**已安装插件的 Host 代码在宿主进程内运行、不受工作区沙箱限制**（plugin-manager README 明示）。
- 错误处理：结构化错误码 + Error: <message> 模型可见结果；取消语义 ABORTED_BEFORE_DISPATCH / ABORTED / TOOL_TIMEOUT。

### 5.3 长任务 job 机制【事实】
- 状态机 running → stopping → completed/killed/failed；id <kind>-<short-uuid>；owner 为 Session，跨 agent 不可见；bounded output ring（stdout/stderr 给模型，log 只给观察者）；updateProgress 发布进度行；结算通知进会话，无需轮询；job/registered 与 job/settled 是持久 Session 事件（含 startedAt/finishedAt/cause/producerReported/detail，**跨重启可审计**）；SDK 通过 session.event 转发；客户端 ClientJobs 提供名册与输出视图。
- **限制**：随附 dsh-jobs-local 是进程内注册表，进程退出任务即消失；跨重启的持久执行需自实现 JobRegistry 后端（README 明示）。适合「训练/推理/下载」这类可断点重跑的任务，但需要自己实现「重启后恢复/重连」策略。
- 相关：dsh-schedule（会话定时提醒，持久、进程存活期间执行）、dsh-spill / output-retention（大输出落盘）、dsh-terminal（持久 PTY 会话）。

### 5.4 子进程与 GPU【事实】
- ctx.subprocess：显式 argv（不经过 shell 解释）、显式 cwd/stdio/环境覆盖、pipe/inherit/collect(+spill)、control pipe（fd 7）、terminate() 幂等、waitForExit() 等待整棵受管进程树停稳；PTY 支持 resize/前台进程组信号；每个组合唯一 provider（本地/远程可替换）。
- 环境清洗：子进程默认不继承凭据类环境变量与 DSH_*，需显式传 env；这点对「训练脚本需要 HF_TOKEN/CUDA_VISIBLE_DEVICES」的场景要么显式传入、要么走 Host 插件自身（插件进程不经过该清洗）。
- GPU 管理：**没有** CUDA/驱动/环境管理 API；可用 nvidia-smi 探测、ctx.subprocess 安装/启动任务、jobs 报告进度；驱动/工具链安装属于系统级操作，需要外部启动器或管理员权限。【事实 + 推断】

### 5.5 用户 DeepSeek API key 与自定义 baseURL/模型【事实】
- 设置 → 模型：DeepSeek 卡片填 key；key 只写、保存后只回脱敏描述符；存 $DSH_HOME/.credentials.yaml，settings 只存凭据引用（docs/user/guide/providers.zh.md:7-15）。
- 第三方/自定义：**添加模型提供商 → 自定义模型 API**，可填 Provider ID、显示名称、基础 URL、API 协议（openai-completions / openai-responses / anthropic-messages）、key、至少一个模型；可「获取可用模型」探测；表单写入 $DSH_HOME/profiles/<profile>/cordis.patch.yml（providers.zh.md:25-60）。
- 路由细节：内置 llm-deepseek（Messages API）支持 baseURL 配置（默认 https://api.deepseek.com/anthropic，回退 $DEEPSEEK_BASE_URL）与 apiKeyEnv（默认 DEEPSEEK_API_KEY）；OpenAI 兼容网关走 llm-pi-ai 的 providers 配置（支持 compat 开关、reasoningEfforts、模型目录覆盖等）。证据：dsh-llm-deepseek/README.zh.md:36,44,57,83；providers.zh.md:60-160。
- 官方账号登录是**可选**路径（deepseek-account-platform 行）；只用 API key 的 Web/Desktop 可以正常使用（user guide 全篇以 API key 为主路径）。
- 默认模型 deepseek-official / deepseek-flash，可由 agent-default-model 或设置页改。
- 对产品的含义：**「用户接自己的 key」无需任何改造**；要预设自家网关则用自定义 provider 或 patch 默认配置。

## 7. 启动器与 DSH 的关系（问题 5）

### 7.1 三种整合方案对比
| 维度 | A. 独立启动器（Tauri/Electron）+ DSH 内核 | B. 启动器=DSH 插件/页面 | C. 混合（推荐） |
|---|---|---|---|
| 形态 | 自研壳/自研前端；DSH 以 dsh web（HTTP+WS）或 --profile sdk（stdio JSON-RPC）运行在后端；或用官方 Desktop 安装包 | 打包成 bundle 装进 DSH profile；启动器功能是一个音乐面板/页面 + Host 插件 | 启动器独立负责环境/安装/更新/服务启停；日常使用进 DSH 桌面/网页（插件套件）；两者共享配置与状态 |
| 复用 DSH 能力 | 需自建聊天/会话/模型设置/审批 UI（或内嵌 DSH Web） | 全部复用（聊天、设置、权限、任务、插件管理、更新） | 全部复用 + 系统级能力自建 |
| 系统级能力（驱动/服务/注册表/托盘/安装） | 强（原生进程、管理员权限、安装器） | 弱（Host 插件同进程、UI 受限；审批/沙箱模型偏开发者） | 强 |
| 产品化 UI/品牌 | 完全自由 | 受 DSH 外壳约束（可加整页，不能去掉聊天壳） | 启动器自由 + DSH 内应用页 |
| 与 DSH 版本耦合 | 低（可通过 SDK 协议/HTTP 适配），但需跟随 SDK/Web API 变化 | 高（插件 API、bundle、client manifest、engines.dsh 强耦合） | 中（启动器弱耦合，插件强耦合但可控） |
| 工作量 | 高（2 套 UI + 进程编排 + 更新） | 低（**最快 MVP**） | 中 |
| 许可/品牌 | MIT，自由 | MIT，自由但受商标规范 | 同左 |
| 风险 | 重造轮子、体验割裂、SDK 协议本身也是 pre-stable | API 破坏性变更、升级需回归、受 DSH 产品方向影响 | 两套状态同步、启动器与 DSH 生命周期协调 |

### 7.2 推荐路线【推断】
1. **阶段一（MVP，4–8 周）**：做一个自有 bundle（music-core Host 插件 + music-ui 客户端插件 + 音乐 skills + 可选 MCP 桥），安装进固定版本的官方 DSH Desktop（或 Web）。复用聊天、模型设置（用户自填 key）、审批、jobs UI、插件管理。验证核心闭环：训练任务提交/进度/日志/取消、音频编辑器页、模型下载管理。
2. **阶段二（产品化，6–12 周）**：fork DSH 做白标构建（appId/productName/图标/更新 feed/裁剪 office 等）+ 做独立 Tauri 启动器：负责首次环境检测（Python/GPU/驱动）、组件安装、模型下载、DSH 进程与插件更新、日志与诊断；启动器启动 dsh web（本地端口 + token）或直接拉起桌面版，提供统一入口。
   - 若希望「用户只看到自己的产品 UI」：改用 --profile sdk（JSON-RPC）或 HTTP/WS 接自研前端，DSH 只做 agent/工具内核；但需自建会话/设置/审批 UI（成本最高）。
3. **不建议**：把启动器完全塞进 DSH 插件（系统级操作与 UI 受限、升级耦合、无沙箱保障）；也不建议一开始就全自研前端（重复成本高、错过 DSH 已交付的 agent 体验）。

| **插件/内容更新（自有插件）** | 自有插件市场索引（dsh-plugin-market 支持用户配置索引 URL）+ plugin_manager 安装；或自研 bundle 更新器 | 官方 plugin market 仅有索引读取，无官方市场 |

| **音频编辑器（编辑/播放/波形）** | 客户端插件：Canvas/WebAudio/React；音频字节经 Host HTTP 路由或 Remote 读写（ctx.fs/workspace files）；或嵌入本地 web 编辑器 iframe | 可行；大依赖需打进 client bundle；导出/编码建议放 Host/外部服务 |
| **GPU 环境管理（探测/展示）** | Host 插件 subprocess 跑 nvidia-smi/where python，页面展示；安装/修复动作交给外部启动器 | 系统级安装不做进插件 |

### 8.2 需 fork DSH（或至少 fork 构建/外壳）
| 能力/需求 | 原因 | 最小改动 |
|---|---|---|
| **白标产品**（名称/图标/appId/协议/更新源/版本号） | productName/artifactName/图标/协议硬编码在 apps/desktop；appId 与 update feed 可环境变量覆盖 | fork apps/desktop 构建脚本与 resources/；1–3 人日 |
| **裁剪发行版**（去 LibreOffice/Office/语音/浏览器/审查器等，减体积） | 依赖树由 @deepseek-ai/dsh-desktop-runtime + bundle 行决定；需要同步改依赖清单、行禁用、runtime 产物与签名 | fork 构建 + 自建 bundle 覆盖行；≈1–2 周含验证 |
| **替换 DSH 外壳/去掉聊天主界面**（若产品要求全屏自有 UI） | root renderer/AppFrame 不开放替换 | fork packages/client/ui-layout/web 壳，或不用 DSH UI 而走 SDK/HTTP 自研前端 |
| **客户端插件构建链/HMR**（仓库外第三方） | clientBundle tsdown preset 与 Typert codegen 不在 npm 包内 | 复制/复刻构建脚本（不必 fork 运行时）；Typert RPC 需自建 codegen 或改用 HTTP 路由 |
| **原生音频/GPU/驱动能力** | Electron 壳为薄壳，插件无 native 通道 | fork Electron 主进程 + native addon（或改为外部服务） |
| **账户/遥测/会话上传默认行为** | session-log-deepseek、session-telemetry-otel、Desktop product telemetry 默认挂载 | 可通过自有 bundle patch disabled:true/环境变量关闭，**不必 fork**（见 §9 风险） |

### 8.3 需外部本地服务（插件只做桥接/UI）
| 能力 | 外部服务职责 | 与 DSH 的接口 |
|---|---|---|
| **GPU 环境管理/训练环境安装** | 驱动/CUDA/torch/venv 检测与安装、权限提升、版本矩阵 | 启动器（Tauri/Electron）或独立 Python 服务；DSH 插件经 ctx.subprocess/HTTP 调用 |
| **音源训练运行时** | 训练脚本、数据预处理、断点续训、GPU 调度 | 独立 Python 进程（uv/pip 环境）+ job 生产者；进度经 stdout/JSONL 回传 jobs |
| **实时变声桥接** | 虚拟声卡/ASIO/低延迟 DSP（Ring buffer、VST/AU 宿主） | 原生服务 + 本地 IPC（WebSocket/命名管道）；DSH 插件只做控制面板/状态 |
| **模型市场/下载 CDN** | 大文件托管、断点续传、镜像、鉴权 | HTTP API；插件或启动器调用 |
| **音频编解码/重采样/分离（FFmpeg/Demucs 等）** | 重依赖、原生库、可能 GPU | 独立服务或命令行；DSH 插件经 ctx.subprocess 调用 |
| **自动更新分发** | feed 托管、签名、灰度 | electron-updater/自研更新器 |

### 8.4 不可行（或明确不建议）
| 需求 | 结论 | 原因 |
|---|---|---|
| 在 DSH 页面内做**低延迟系统级音频路由/虚拟声卡** | 不可行 | 浏览器/Electron 渲染进程无 native 音频设备通道；webview 无 Node；必须外部服务/驱动 |
| **完全替换 DSH 外壳**且不 fork | 不可行 | root renderer/AppFrame 不开放；只能加整页与 slot |
| 无代码签名做**自动更新静默安装**（Windows 用户机） | 不可行（实践上） | Windows 代码完整性与 SmartScreen 会拦未签名安装包；需 EV 证书/签名链 |
| **一键安装任意 GPU 驱动/训练环境** | 不建议 | 驱动/许可/管理员权限/硬件兼容风险不应由插件进程承担；应独立安装器 + 明确用户授权 |
| 把「DSH」或「DeepSeek Harness」当自家产品名 | 不可行（法律/规范） | 商标规范禁止；可用 DSH 缩写或描述性表述 |
| 依赖 DSH 官方市场做商业分发 | 不可行（当前） | 目前**没有官方插件市场**，只有用户自填索引（plugin-market README 明示） |

## 9. 风险清单

1. **API 稳定性（高）**：DSH 自述 developer preview、会有破坏性变更（README:8-14）；两个月内 6 个 upgrade-guide 版本（0.1.7-rc.2、0.2.0-rc.2、0.2.1-alpha.1~4），且随附包几乎每天发版。插件需声明 engines.dsh 并锁定 DSH 版本；升级要回归（客户端 slot 名、Remote schema、job 事件、manifest 字段都可能变）。
2. **第三方插件安全模型（高）**：已安装 Host 插件在宿主进程内运行、**不受工作区沙箱限制**；安装 git 源码包的 prepare 脚本会在装机器上执行（需用户批准）；插件可访问凭据、文件、网络。对 C 端用户意味着必须自建签名/审核/权限说明，避免用户装来路不明插件。
3. **客户端插件工程门槛（中高）**：官方 clientBundle tsdown preset、Typert codegen、locale 字典、slot 类型合并不在 npm 包内；仓库外团队要复制构建链；bundle 只能请求冻结的 PLATFORM_MODULES，否则自带依赖进 bundle（体积膨胀、版本冲突风险）。
4. **UI 约束（中）**：无 URL 路由/深链；不能换壳；HMR 重载丢 React 状态；single 槽位替换有覆盖风险；桌面 webview/iframe 与主页面跨源隔离（集成靠 postMessage/HTTP）。
5. **分发/签名/更新基建（中高）**：Windows EV 证书（硬件令牌）、macOS 公证、feed 托管与灰度、版本身份（壳+runtime 同版本）都要自建/接手；未签名包在企业环境不可用。仓库提供完整脚本，但需要证书与发布账号。
6. **体积与性能（中）**：安装后 ~1.04 GB；Electron + 内置运行时 + Python/Node；CPU/内存占用对低配用户不友好；启动速度与首屏（Host 启动、loader 组装、client bundle 物化）需实测。
7. **隐私/遥测默认值（高，需处理）**：dsh-base 默认挂载 session-log-deepseek（随 DeepSeek 请求上传未接受的日志事件，单次上限 8 MiB）与 session-telemetry-otel（默认 FEEDBACK_ONLY，DSH_TELEMETRY_DISABLED 可关）、匿名用户 id；Desktop 另有产品埋点（OTLP 到 deepseek collector）。音乐产品涉及用户音频/版权内容，**必须在自有 bundle 中显式关闭/替换并做隐私说明**。【事实：base patch L43-44,218-225；sdk-minimal README 8MiB；telemetry README】
8. **合规/内容风险（中）**：用户上传音频、生成翻唱/克隆音色涉及版权/人格权；模型市场分发的模型许可需逐一确认；MIT 只覆盖 DSH 代码，不覆盖模型权重与第三方素材。
9. **品牌/商标（中）**：见 §6.4；产品命名与宣传需避开「DeepSeek Harness」全称。
10. **产品方向耦合（中）**：DSH 官方正在快速补齐 plugin market、agent team、voice input、browser 等能力；若与我们功能重叠，需评估「跟随上游 vs 自研差异化」。
11. **平台覆盖（中）**：本机为 win32-x64；Desktop 有 macOS 流程但未实测；Linux 仅 Web/CLI；GPU 训练多为 Linux，需要 DSH Web（浏览器访问）或自研服务。
12. **测试/回归成本（中）**：插件需自建 e2e（DSH 仓库的测试基建不随 npm 发布）；客户端 UI 回归需 Playwright + DSH Web。

## 11. 结论与建议

- **可行性结论**：作为「AI 音乐插件套件 + DSH 页面」可行且工作量可控；作为「完全自有品牌的完整桌面产品」也可行，但需要 fork 构建 + 独立启动器 + 自担签名/更新/安全/合规，属于中大型工程（推断：从零到可分发 MVP 约 2–3 个月/2–3 人，产品化再 2–3 个月）。
- **核心建议**：
  1. 先做 Host 插件（工具+jobs+subprocess）+ 客户端整页 的 MVP，验证「训练任务管理 + 音频编辑器 + 模型下载」三条主线；
  2. 用自有 bundle + 自建插件市场索引做分发与更新；不要依赖官方市场（不存在）；
  3. **锁定 DSH 版本**（如 0.2.1-rc.2 / 后续 stable），把 DSH 当作可替换的内核，所有音乐逻辑放自有插件/服务，避免把业务写进 DSH 内部包；
  4. 启动器与 DSH 解耦：启动器负责环境/安装/更新/服务，DSH 负责 agent 与页面；若必须单窗口自有 UI，走 --profile sdk + 自研前端（成本最高，慎选）；
  5. 产品命名遵循品牌规范（用 DSH 缩写/描述性表述），处理好遥测/会话上传默认值。
- **需要 Lead 决策的点**：产品形态（DSH 内页面 vs 独立启动器 + 自有前端）、是否接受 fork/白标与自建更新基建、首发平台（Windows x64 only？）、GPU/训练是否首发、实时变声是否纳入首版。
